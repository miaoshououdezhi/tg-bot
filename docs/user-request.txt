一、项目目标

创建一个安全、无内置广告、部署简单的 Telegram 双向聊天机器人。

主要用途：
访客通过机器人联系管理员，管理员通过机器人回复访客，
双方无需互加好友，且不同访客之间的消息必须严格隔离。

这里的“无广告”包含：
- 项目本身不植入广告、推广链接、付费引流或无关机器人。
- 不加入与必要功能无关的统计、追踪和数据上传。
- 使用 Cloudflare Turnstile、限流、重复消息控制和封禁降低广告骚扰。
- 不宣称可以完全阻止真人广告或人工代过验证。

三、核心聊天功能

1. 访客通过 Telegram 私聊机器人联系管理员。
   第一版采用单管理员、多访客模式，管理员在与机器人的私聊中处理消息。

2. 支持：
   - 文字
   - 图片及图片说明
   - 文件及文件说明
   - 语音

3. 明确处理多张图片或媒体组的方式，确保内容不串线、不静默丢失。
   其他未支持的消息类型应给出简短中文提示。

4. 管理员使用 Telegram 的“回复”功能回复对应消息，
   机器人将内容发送给原访客。

5. 每名访客提供稳定的会话编号。
   管理员可查看该访客的 Telegram 数字 ID、当前昵称、
   验证状态、封禁状态和会话处理状态。

6. 所有回复通过持久化消息映射确定接收人。
   不能依赖昵称、用户名或消息正文中的用户编号进行路由。

7. 多名访客同时发送消息、管理员交错回复时，不得发生串线。

8. 管理员无对应消息可回复时，不猜测接收对象。
   明确提示管理员回复一条有效的访客消息。

9. 明确消息来源和身份信息的展示方式。
   不默认向访客暴露管理员的个人身份信息，
   也不把机器人通信宣传为完全匿名。

四、Cloudflare Turnstile 验证

1. 未验证访客必须先完成验证，消息才能转交管理员。

2. 验证通过后有效期为连续 24 小时，从服务端确认成功时计算。
   普通发消息不能自动延长验证有效期。

3. 超过 24 小时后，下一次发消息必须重新验证。
   已转交管理员的历史消息不因验证过期而自动删除。
   验证过期默认只限制访客继续发送新消息，不阻止管理员回复历史消息。

4. 未验证消息不转交管理员，也不保存为等待自动补发的队列。
   验证成功后，明确提示用户返回 Telegram 重新发送。

5. 优先提供适合 Telegram 内使用的验证页面。
   页面具备加载、成功、失败、过期和重试状态。

6. 后端必须校验 Telegram 身份及 Turnstile 验证结果，
   并将本次验证绑定到对应 Telegram 用户。
   不能信任前端自报的 user_id 或仅凭前端成功提示放行。

7. 防止伪造身份、跨用户使用验证结果、重复提交和并发重放。

8. Cloudflare 超时或验证服务异常时：
   - 不创建新的验证通过状态。
   - 不自动放行全部用户。
   - 提供重试提示。
   - 不无故撤销其他仍在有效期内的验证状态。

9. 已封禁用户不能通过重新验证解除封禁。

五、Telegram 内管理功能

主要管理操作在 Telegram 中通过按钮完成，
第一版不要求额外搭建网页管理后台。

至少提供：

1. 管理面板
   - 查看待处理会话。
   - 查看会话状态和访客资料。
   - 会话列表支持必要的分页，避免按钮和消息过长。

2. 封禁与解除封禁
   - 封禁前显示目标会话和确认按钮。
   - 可以取消本次封禁操作。
   - 封禁后可以解除封禁。
   - 解除封禁后仍按当前验证有效期判断是否允许发消息。

3. 要求重新验证
   - 管理员可使某个用户的现有验证失效。
   - 操作前支持确认和取消。

4. 手动允许联系
   - 管理员可为指定访客手动授予 24 小时联系权限，
     用于处理验证页面不可用等情况。
   - 显示授权来源和到期时间，并允许撤销。
   - 对封禁用户必须先明确解除封禁，不能暗中绕过封禁。

5. 会话处理状态
   - 支持标记“待处理”“已处理”。
   - 支持重新打开已处理会话。
   - 访客发送新的有效消息后，会话恢复为待处理。

6. 按钮操作规则
   - 区分“执行前取消”和“执行后撤销”。
   - 对无法真正撤销的操作明确说明，不提供虚假的撤销按钮。
   - 重复点击、过期按钮和状态已经变化时，给出清楚提示。
   - 每次点击均检查管理员身份和操作目标。
   - 不能仅因按钮出现在某条消息上就认为有管理权限。

管理员回复消息本身不需要每次二次确认，
保持日常聊天操作顺畅。

六、反广告与反滥用

1. 实现按用户的消息频率限制和必要的全局保护。
   具体阈值自行选择合理默认值，并允许配置。

2. 对验证申请、验证提交和机器人提示分别限流，
   避免用户刷消息导致机器人持续刷提示。

3. 限制同一用户短时间重复发送相同内容。
   避免只用文字相同就永久封禁，减少误伤。

4. 文字、媒体、说明文字等入口使用一致的访问控制，
   防止通过不同消息类型绕过验证或封禁。

5. 提供可配置的链接限制策略，默认不一刀切禁止所有正常链接。

6. 对文件大小、请求体、未完成验证会话数量及过期数据
   设置必要限制与清理机制。

7. 不默认引入 AI 广告识别或付费第三方审核服务。

七、交互与消息反馈

1. 所有面向用户和管理员的提示使用简洁中文。

2. 首次使用时说明：
   - 这是联系管理员的机器人。
   - 需要先完成验证。
   - 支持的消息类型。
   - 验证后需要重新发送。
   - 请勿发送密码、验证码等敏感信息。

3. 提供准确的投递反馈：
   - 已接收、已转交、发送失败应有明确语义。
   - 不把“发送成功”显示为“管理员已读”。
   - 避免对每一步都发送额外提示，造成聊天刷屏。

4. Telegram 超时、限流、管理员未启动机器人、
   访客拉黑机器人或其他投递失败时，应有适当处理和反馈。

5. 对发送结果不确定的情况记录状态并采取保守恢复策略，
   不盲目重试导致同一消息重复发送。
   明确说明无法保证的投递语义。

6. 提供可配置的欢迎说明和离线提示。
   同一访客短时间内不要重复收到相同离线提示。

7. 提供简单的管理员快捷回复。
   由管理员主动选择发送，不默认代替管理员自动回答。

八、安全与隐私

1. Bot Token、Turnstile Secret 等秘密通过环境变量或秘密文件注入。
   不提交到 Git，不写入镜像，不输出到日志或测试报告。

2. 配置示例只能使用占位值。
   区分可以公开的 Turnstile Site Key 和必须保密的 Secret。

3. 默认尽量少保存聊天正文和附件。
   尽可能通过 Telegram 已有消息和文件标识完成转送。

4. 对身份数据、消息映射、验证记录和日志定义明确的保留与清理策略。
   映射清理后，管理员回复过旧消息应得到清楚提示，不能误投递。

5. 日志默认不记录完整聊天正文、完整验证凭证或包含秘密的请求地址。

6. 做好网页输出编码、请求校验、管理员权限检查、
   回调授权和代理请求头信任边界。

7. 不依赖隐藏按钮或难以猜测的用户编号作为安全措施。
